# DDD ユースケース層ポリシー

ユースケースは、読み込み、ドメインに判断させ、永続化する調整役に留め、どのステップも再実行して安全にする。

## 原則

| 原則 | 基準 |
|------|------|
| 調整し、判断しない | 業務判断はドメインの操作が行う。ユースケースは読み込み、呼び出し、保存する |
| ID と値を受け取る | コマンド側の `execute` は ID と値オブジェクトを受け取り、集約は受け取らない |
| 1 要求に 1 ユースケース | ユースケースから別のユースケースを呼ばない |
| 繰り返しても安全 | 各ステップについて、再実行しても安全な理由を示す |
| 回復を明示する | 複数集約のフローは Process Manager か明示的な再実行戦略で回復する |
| 更新は書き込みモデルが決める | 更新をクエリ側の読み取りモデルから判断しない |

## ユースケースの形

| 基準 | 判定 |
|------|------|
| コマンド側の `execute` が集約、Entity、またはプリミティブを包んだリクエスト DTO を受け取る | REJECT。ID と値オブジェクトを受け取り、リクエストからの変換はアダプタで行う。入力 DTO を渡すという一般的な指針は、クエリ側のユースケースにだけ当てはまる |
| ユースケースが別のユースケースの `execute` を呼ぶ | REJECT |
| ユースケースがドメインの getter を読み、比較・計算・分岐に使う | REJECT。判断をドメインの操作へ移す |
| getter の結果を、そのまま、または不変のローカル変数経由でリポジトリポートのメソッドに渡す | OK |
| ユースケースがデータベースや RPC のクライアントを直接使う | REJECT。ポートを通す |
| ポートを、ポートの型を付けたフィールドや引数で持つ | OK |

## 整合性と再実行

| 基準 | 判定 |
|------|------|
| 再実行しても安全な理由が示されていないステップがある | REJECT |
| 加算型（accumulation）のコマンドに要求 ID の記憶がない、または直前の要求しか覚えていない | REJECT |
| 永続化の結果が不明なときに、要求 ID などの証拠で照合せず再試行している | REJECT |
| 初回成功、重複成功、拒否を呼び出し側が区別できない | REJECT |
| 反映済みの要求 ID の再試行を、状態や不変条件による拒否より後で判定しているため、後続のコマンドで状態が変わると拒否（`AlreadyIssued`）として返り得る | REJECT。記憶した要求 ID を最初に判定し、重複成功を返す |
| 永続化が成功する前にイベントや新しい状態を公開している | REJECT |
| upsert であることを冪等性の十分な根拠として示している | REJECT。冪等性の戦略を示す |

## 複数の集約

| 基準 | 判定 |
|------|------|
| 明示的な戦略なしに、1 つのトランザクションで複数の集約を変えている | REJECT |
| 複数集約のユースケースに、Process Manager も再実行の根拠もない | REJECT |
| 対象の集約がすべて `programming_model: actor` なのに Process Manager を使っていない | REJECT |
| 集約をまたいだ自動ロールバックを約束している | REJECT。補償は新しい業務操作である |

## 読み取りモデル

| 基準 | 判定 |
|------|------|
| 更新の判断にクエリ側の読み取りモデルを使っている | REJECT。復元した集約で判断し、期待バージョンや制約で守る |
| コマンド側のユースケースがクエリ側のパッケージに依存している | REJECT |
