# DDD ユースケース層ポリシー

標準は Event Sourcing。リポジトリの読込は `Result<Aggregate | undefined, RepositoryError>`（Rust は `Result<Option<Aggregate>, RepositoryError>`）、保存は `Result<void, RepositoryError>`（Rust は `Result<(), RepositoryError>`）を返す。保存の入力は、集約 ID を持つドメインイベントと、コマンドを実行した後の集約（スナップショット）で、`store(event, snapshot)` と呼ぶ。集約 ID を別に渡さない。イベント履歴の取得と replay はリポジトリ内部に置き、ユースケースは取得した集約でコマンドを実行し、イベントの保存成功後に結果を返す。操作別 Result の単なる別名や余計な戻り値ラッパーを作らない。再利用する型はジェネリックにし、インフラの失敗は共通の `RepositoryError` で返す。

ユースケース層のコードを判定する。ユースケースは読み込み、ドメインの操作を呼び、保存する調整役である。扱うのは、ユースケースの形、再実行と公開、複数の集約、読み取りモデルでの判断である。判断の置き場所とコマンド ID の記憶はドメイン層ポリシー、依存してよい先は層の依存ポリシーが持つ。

## ユースケースの形

| 基準 | 判定 |
|------|------|
| コマンド側の `execute` が集約、Entity、またはプリミティブを包んだリクエスト DTO を受け取る | REJECT。ID と値オブジェクトを受け取り、リクエストからの変換はアダプタで行う。入力 DTO を渡すという一般的な指針は、クエリ側のユースケースにだけ当てはまる |
| ユースケースが別のユースケースの `execute` を呼ぶ | REJECT |
| ポートを、ポートの型を付けたフィールドや引数で持つ | OK |
| ポートを持つフィールドや引数の名前が、ポートの名前に合っていない（`InvoiceRepository` なら `invoice_repository` や `#invoiceRepository`）。たとえば `invoices` のような集約の複数形 | REJECT |
| `execute` を持つ型の名前が `<動詞><対象>UseCase`（`IssueInvoiceUseCase`）になっていない | REJECT。関数だけで書いたユースケースには名付ける型がない |

## 再実行と公開

| 基準 | 判定 |
|------|------|
| 再実行しても安全な理由が示されていないステップがある | REJECT |
| 永続化の結果が不明なときに、コマンド ID などの証拠で照合せず再試行している | REJECT |
| コマンドの初回成功、重複成功、拒否を、呼び出し側が区別できる形で返していない | REJECT |
| 永続化が成功する前にイベントや新しい状態を公開している | REJECT |
| リポジトリポートの `Result` を捨てている、または保存に失敗したのにイベントを返している | REJECT。失敗をユースケースのエラーとして返す |
| upsert であることを冪等性の十分な根拠として示している | REJECT。冪等性の戦略を示す |

## 複数の集約

| 基準 | 判定 |
|------|------|
| 明示的な戦略なしに、1 つのトランザクションで複数の集約を変えている | REJECT |
| 複数集約のユースケースに、Process Manager も再実行の根拠もない | REJECT |
| 対象の集約がすべて `programming_model: actor` なのに Process Manager を使っていない | REJECT |
| 集約をまたいだ自動ロールバックを約束している | REJECT。補償は新しい業務操作である |

## 読み取りモデル

| 基準 | 判定 |
|------|------|
| 更新の判断にクエリ側の読み取りモデルを使っている | REJECT。復元した集約で判断し、期待バージョンや制約で守る |
