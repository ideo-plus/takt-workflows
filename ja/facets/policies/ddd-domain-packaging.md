# DDD ドメインのパッケージ名ポリシー

ドメイン層のパッケージとモジュールの名前と、型をモジュールにまとめる方法を定める。モジュールはエヴァンスのいうモジュールであり、凝集した概念をまとめるモデルの一部である。名前はユビキタス言語から付け、技術分類では付けない。名前に対応する業務用語の宣言（集約写像の `domain_packages`）はドメインモデルポリシーが持つ。

| 基準 | 判定 |
|------|------|
| パッケージやモジュールの名前が `aggregate(s)`、`impl(s)`、`implementation(s)`、`vo(s)`、`entity`、`entities`、`value_object(s)`、`valueobject(s)`、または単独の `domain` | REJECT |
| 一つのモジュールに一つの集約、または業務上凝集した複数の集約を置く | OK。個数で固定しない。集約ごとの不変条件と整合性を守る境界は維持する |
| モジュールを共有することを理由に、独立した集約の整合性境界を統合する | REJECT。集約境界はドメインモデルの不変条件から判断する |
| 業務上のまとまりを示さず、集約とモジュールの一対一対応を強制する | REJECT |
| 同じ階層のモジュール間に循環する依存がある | 警告。依存を一方向にする案を検討し、残すなら業務上の理由を `domain_packages` の `rationale` に示す |
| 親子モジュールの依存を、同じ階層の依存と同じ基準で機械的に拒否する | REJECT。循環を避ける案を検討したうえで、親子関係の必要性を判断する。ただし言語・層の依存規則は引き続き守る |
| モジュール数や集約数だけを理由に、境界づけられたコンテキストを増やす | REJECT。モデルの用語や規則を分ける根拠を確認する |
| 同じ業務概念の集約、Entity、値オブジェクトを、型の種類だけでモジュールに分けている | REJECT |
| 1 つの業務概念に属する型（集約ルートの識別子、その値オブジェクト、集約が記憶するコマンド ID）を、その概念のモジュールの外に置いている（`invoice` の隣の `invoice-id`） | REJECT。その概念のモジュールの下（`invoice/invoice-id`）に置く |
| ドメインのパッケージのルートに概念が並び、どれとどれがまとまりなのかが読み取れない | REJECT。凝集する概念をユビキタス言語の名前のモジュールにまとめ、モジュール同士の依存を少なくする |
| 概念が少ないあいだ、複数の概念が使う値（`money`）やほかの集約を指す ID（`customer-id`）を、責務の名前のモジュールとしてルートに置く | OK |
| 共有する値を、責務の名前（`money`、`address`）のモジュールではなく `common/vo` のような入れ物に置いている | REJECT |
| `common`、`shared`、`utils` がドメインの概念を持っている | 警告。業務用語としての根拠を示すか、名前を変える |
| `-domain` の接尾辞や `packages/domain` の配置のような層の標識 | OK。技術分類ではなく層の標識である |

`aggregate/`、`model/`、`services/`、`repositories/` のようにコードを種類でまとめるディレクトリの例は、ドメイン層のコードには当てはまらない。
