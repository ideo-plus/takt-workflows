## DDD model changes

The project keeps its DDD settings in `.ddd.toml` and its model in `docs/ddd/domain-model.yaml`, `docs/ddd/aggregate-mapping.yaml`, and `docs/ddd/layer-structure.yaml`. The plan states the exact changes to these files; the implementation applies them before any code.

- Read the four files. When `.ddd.toml` is absent, plan to create it with the languages the change touches, `module_layout = "file"` for Rust, and `module_layout = "named-file"` with `code_representation = "class"` for TypeScript, unless the request states other choices. Do not infer the layout from existing files. When a model file is absent, plan to create it.
- State the meanings of terms this change touches, business examples, and unconfirmed assumptions. Establish meanings and boundary rationale per Context, contacts with other models, information suppliers and consumers, and responsibility for adoption, sharing, or translation. State when no relationship is involved. Record rationale in the plan report with references to existing model elements; add no unsupported declaration keys or unrelated artifacts.
- Use business examples and counterexamples to assess model responsibilities and client operations. Explain alternatives and the chosen model where judgment is needed. When implementation or tests reveal a model problem, incorporate its evidence, affected elements, and changes to declarations, mappings, code, and tests into the plan.
- Derive Aggregate boundaries from immediate invariants. For cross-Aggregate rules, state tolerated delay, intermediate states, retries, and compensation conditions; distinguish atomic guarantees from eventual consistency. Explain element classifications through the need to track identity and attribute-based replaceability, and establish the scope and lifetime of stable Entity identity.
- Derive Aggregate-owned business operations in this order: past-tense domain events, the commands and actors that produce them, the aggregates whose state they change, and the invariants that hold those aggregates together. For an independent decision or calculation producing no event, assess Domain Service selection criteria and current declaration support; invent no event or Aggregate to force it through this derivation.
- Reuse existing element IDs from an accepted model. A business rename changes `name` only; record every split, merge, and deprecation in `lineage`. When an unaccepted plan or an artifact generated in this task violates the schema, correct its invalid IDs and every reference to valid `<kind>.<segments>` IDs. This repairs declarations rather than renaming established elements; retain no old-ID aliases or compatibility paths.
- Follow the declaration schema examples in the knowledge. Repair schema violations during planning rather than treating them as unresolved business requirements; record the old-to-new ID mapping and its rationale.
- Do not treat preservation of public APIs, type names, or test expectations from existing code or an earlier plan as a user requirement. When correcting unaccepted code generated in this task, or when the user requests migration without backward compatibility, plan to replace policy-violating APIs together with callers and tests. Retain no aliases, empty implementations, or forwarding methods for obsolete APIs, and do not request confirmation again for authorized corrections. For an accepted external contract, verify that the requested scope includes its change.
- Add a `## DDD Model Changes` section with the YAML to add or change, per file:
  - domain model: every new or changed aggregate with its invariants, and every command and factory rule with its domain errors, state effect, transitions, the one event it produces (`event`), and idempotency strategy
  - aggregate mapping: for every aggregate its `programming_model` and `persistence_method`, its package, module path, type, ports, and repository; for every operation its method, error type, and error cases, and for every command its `success_type`; `replay_methods` for event-sourced aggregates; `domain_packages` entries with business term, model references, and rationale for every package and module level the change places code in
  - layer structure: packages, dependencies, ports, repositories, and restoration paths the change adds or changes
- Explain the Module partition. In each `domain_packages` entry, use `model_refs` and `rationale` to state the business concepts grouped, why they should be understood together, and dependencies on other Modules. Allow one Aggregate or several cohesive Aggregates per Module. Explain splits, merges, or renames of existing Modules and the mapping changes; when the reason for separate models is unclear, consider Modules before adding a Bounded Context.
- Add a `## DDD Use Cases` section declaring, for each use case the change adds or changes: `use_case_id`, `name`, `target_aggregates`, `commands`, `re_execution_basis`, `recovery_policy`, `multi_aggregate_strategy` when it targets several aggregates, and `read_model_exposure`.
- In the completion contract table, the first rows apply the DDD model changes. Every implementation row cites the model IDs it implements, and its implementation location follows the aggregate mapping and the selected module layout.
- Every Domain Primitive must declare domain invariants narrower than its backing type and a parse factory rule whose preconditions include all of them. Provide both of and parse, validating the same invariants before initialization: of assumes valid input and panics or throws on a caller contract violation, while parse returns invalid input as Result. Do not create a DP when the backing type alone expresses the domain. Resolve unspecified value rules as open questions; never silently omit the rule or create an unconstrained DP.
- When the request leaves a business rule undecided (an invariant, an error condition, an idempotency requirement), list it as an open question with the assumption the plan uses; do not present an invented rule as a requirement.
- For numeric conversion during initialization, state the input and storage types and how finiteness, integrality, and bounds are checked. When replanning after an inspection failure, explain why the previous form was not recognized and the expected result of the changed form; do not repeat the same expression or merely relocate the cast.
- When considering a new or changed Domain Service, add "Domain Service Decisions" to the plan report and record the responsibilities, inputs/outputs, business rules, existing model references, placement, rationale, and alternatives specified in the knowledge. Establish independence from invocation history, no persistence, and no displacement of Aggregate-owned decisions. Treat an independent operation that the current declarations cannot express as a contract gap; invent no unsupported keys or artificial Aggregates.
- Do not read under `.takt/`: the DDD rules are in the policies and knowledge given to this step, and the ddd-lint checks are found by running it, not by reading its sources.
